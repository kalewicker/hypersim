## Requested scope and refusal behavior

Use strict typed receipt paths and requests with no unknown fields. Permit
only the declared complete protocol/grammar, fixed ordinary world, metadata-
isolated allocator, opt-in repeated-self-pair feasibility matcher, MaxParallel
with one rewrite, pooled work/results exactly 50,000, 183 finite logits and
one bounded engineering evaluation at exactly 100 steps. Caller seeds are
explicit inputs, not replacements for any historical experiment.

Separate evidence verification, preflight readiness and actual execution.
An opaque prepared capability is created only after checking the request,
all required receipts, predicates and current implementation pins. Serialized
pass flags or manifests cannot be deserialized into an execution capability.
Recheck evidence and source identity at the execution boundary. Recompile the
grammar and require the registered catalogue hash before emission/evaluation;
do not hydrate trusted native programs from caller-provided JSON.

Missing, stale, tampered, extra-file, unsafe-path, symlink, failed or mismatched
evidence; wrong protocol/grammar/allocator/matcher/limits; nonfinite/wrong-width
parameters; and full-training/10,000-step requests must fail before grammar
compilation or physics. Refusal artifacts record zero optimizer, precheck,
held-out and bounded-evaluation steps. Fresh output is required; never place
output inside a prerequisite archive or overwrite an existing directory.

The bounded runner uses the unchanged native evaluator at 50k/50k and retains
null fitness for any cap/invalid/nonadvancing trajectory. No retry, fallback,
fuel refill, cap increase or score substitution. It records the emitted
production, all native steps, usage and configuration in an engineering-only
receipt. It is not an optimizer campaign or training admission.

## Verification and limits

Pure preflight has zero grammar compilations and Engine steps. Regression-test
malformed/unsupported requests, archive coverage and paths, altered gate
predicates, stale source pins, runtime-vs-classification scope confusion,
output preservation and opaque execution boundary behavior. Use real sealed
archives for positive admission and negative provenance tests; small synthetic
fixtures are unit tests only, never scientific receipts.

At most one integrated accepted engineering job is proposed for verification:
one grammar rebuild, 100 native steps, zero optimizer/precheck/held-out work,
900-second wall and 512-MiB output ceilings. A failure is preserved, not retried
as a new accepted job. Additional native unit controls remain development
evidence. Freeze implementation, binary, request, contract and audit tool
before that engineering job; seal every output except the root seal itself.

CLI preflight must perform no physics. A distinct bounded-execution command
is explicit; no full-training command or authorization flag is added. Existing
legacy campaign and complete-vocabulary rejection guards remain unchanged.
The reserved 20×16×10,000-step campaign is not launched. Further training needs
its own fixed schedule, objective, null denominators, scaling/resource policy
and explicit user launch approval; a 100-step receipt cannot supply those facts.
