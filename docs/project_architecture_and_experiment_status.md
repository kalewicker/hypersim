## 1. What this project is

Hypersim is a deterministic research workbench for **hypergraph rewriting**.
It lets a user define a graph-rewrite substrate in TOML, execute it under a
well-specified conflict model, observe it through multiple independent
instrument layers, and persist a reproducible scientific record.

The project currently contains four interconnected research programmes:

1. **Substrate / event-alphabet characterisation** — what fixed rewrite-rule
   sets actually explore, measured with `hg-alphabet`.
2. **Artificial life (ALife)** — rule-defined carrier ecology, lineage and
   selection, with causal-emergence measurements across the replication
   boundary.
3. **Locality / leakage (LK)** — production and removal of non-local
   structural handles, including cone, twin, closure, and ledger instruments.
4. **Cognition and self-modification** — learned rule-selection policies and
   a separately reified, mutable rule ecology.

The project is deliberately conservative about claims.  In particular,
completed execution does not make a metric valid: null controls, calibration,
instrument engagement, stationarity, reproducibility, and an explicit
epistemic tag are recurring gates throughout the documentation.

## 2. Architectural rules that should not be casually broken

These are the load-bearing boundaries for an extension:

- `hg-core` owns graph identity and snapshots; `hg-schema` owns stable,
  serializable result shapes.  Do not make either depend on higher-level
  simulation code.
- `hg-observe` owns the engine-facing extension vocabulary.  Observers and
  policies depend *downward* on it; it never depends on matcher, conflict, or
  apply code.
- **Only `hg-sim-core` imports `hg-engine` as an orchestrator.** A feature that
  changes what happens during a step should normally use an observer or
  `RuleSelectionPolicy`, rather than importing the engine into a new crate.
- `hg-output` has no internal crate dependency.  It writes generic serde rows,
  manifests, and opaque bytes; callers supply domain objects.
- The physical dynamics are shared.  Training rollouts call the same internal
  step loop as scientific runs and merely disable disk writes.
- Optional research layers are feature gated.  A build without `alife` or
  `cognition` must remain bit-identical to the substrate-only behavior.
- The rule file is part of the experiment, not just configuration.  Treat it,
  the config, seed, feature set, and manifest as reviewable provenance.

There is one important documentation-time distinction: older `README.md` /
v4-plan wording calls ALife and cognition “reserved.”  The current workspace
does contain `hg-alife`, `hg-cognition`, and `hg-train`; source and current
findings take precedence over that historical wording.

## 3. Dependency and control flow

### 3.1 Crate layering

```text
                         hg-gui (egui; live feature)
                                  |
CLI / GUI / hg-train  -->   hg-sim-core  <--- configuration + rule files
                                  |
     +----------------------------+-----------------------------+
     |             |              |              |              |
 hg-engine       hg-eval       hg-causal      hg-output      hg-report
     |             |              |              |              |
 hg-rules     hg-observe ---- hg-schema ----- hg-app-api      (schema)
     |             |              |                              
     +-------------+--------------+                                
                   |
                hg-core

Optional integrations into hg-sim-core:
  hg-alife (biology observer + motif classifier + embedded rules)
  hg-cognition (RuleSelectionPolicy implementation)
```

`hg-parallel` is a Rayon re-export used behind the engine's `parallel`
feature.  `hg-selfmod` is intentionally separate: it uses the real engine's
public matcher/conflict/apply functions through a library driver rather than
modifying the production step loop.

### 3.2 One simulation step, end to end

```text
SimConfig TOML
  -> load built-in/file/inline rules; compile and validate
  -> construct initial HypergraphStore
  -> [optional] append ALife rule biology / install policy / install observers
  -> Engine step:
       creation schedules -> pattern bindings -> optional policy selection
       -> deterministic conflict resolution -> sequential application
       -> RewriteEvent fan-out to ObserverChain
  -> at each metrics window:
       evaluator + causal observers -> MetricsRow / summaries / live DTO state
       -> CSV row, snapshot/logs, lossy GUI progress event
  -> terminal transition:
       manifest sealed -> report rendered -> durable status event
```

Candidate collection may be parallel, but accepted bindings are sorted before
application.  A policy may choose candidates; it cannot bypass node-disjoint
conflict resolution.  This is the central safety property to preserve when
adding learning or steering.

## 5. The substrate data model and rewrite contract

### 5.1 Core values

- Nodes and edges have generational SlotMap identifiers (`NodeId`, `EdgeId`),
  so stale references are detectable rather than silently reused.
- A node has a label and a sparse property map.  `PropertyValue` supports
  `Int`, `Float`, and `Bool`; persistent snapshots use a tagged wire form so
  the variants survive bincode round trips.
- Hyperedges contain unordered endpoint sets for canonical hashing.  The
  `GraphSnapshot` is a borrowed, read-only view exposed to observers,
  classifiers, and policies.
- Canonical hashing sorts live nodes by logical contents, remaps edges through
  that ordering, sorts the remapped endpoint sets/edge list, and uses a
  deterministic hasher.  It is a reproducibility identity, not a general
  graph-isomorphism algorithm.

### 5.2 TOML rule language

Rules declare an LHS pattern and an RHS rewrite.  Labels are *sparse maps*: a
missing entry means unconstrained, avoiding placeholder/null ambiguity in TOML.
Patterns can include node/edge labels, property guards, derived-quantity
guards, and comparisons between matched variables.  Effects include literals,
copy/scale, arithmetic updates, and jitter; fresh RHS nodes may be effect
sources because effects occur after RHS-node creation and before RHS-edge
creation.

Creation rules have an empty LHS and a mandatory schedule (`once` or
`every_n_steps`).  Ordinary rules may not have a schedule.  This validation is
important: scheduled production joins the ordinary candidate pool, but has an
empty binding and hence conflicts with nothing.

The latest grammar extensions worth knowing about are property comparison and
node-quantity comparison (currently degree).  Both were added to express real
experimental needs, and both have parser, firing, and determinism tests.  A
new guard must not be added only to make one result possible; it should have a
stated domain and a test in which it rejects a candidate.

### 5.3 Matching, conflict, and application

1. The matcher enumerates bindings; matching is non-injective by default
   unless a rule/guard says otherwise.
2. Guards are checked in declared order.  Some comparisons are necessarily
   post-binding filters because both variables must already be bound.
3. Candidate bindings are ordered using priority (higher first) and stable
   tie-break information.  The conflict resolver accepts a node-disjoint set.
4. Accepted bindings apply in that resolved order.  A per-step seeded RNG is
   consumed only by operations that need it (for example, `jitter`), in that
   stable declaration/application order.
5. Observers receive read-only rewrite events after application.  They may
   measure; they must not mutate substrate dynamics.

Consequences for maintainers:

- Do not make a guard's evaluation order hash-map dependent.
- Do not replace a conflict check with a global “phase” unless that phase is
  itself part of the specified physics.  MaxParallel permits disjoint removal
  and production bindings in the same step; this is a measured consequence in
  the locality work.
- Candidate enumeration cost can dominate even when a later guard is selective
  (`swap` is the concrete quadratic-LHS example).  A post-binding guard does
  not make enumeration cheaper.

## 6. Reproducibility, persistence, and report semantics

### 6.1 Determinism policy

For a fixed config and seed, the final canonical graph hash is exact.  CSV
rows are cell-wise equal within the documented float tolerance after excluding
intentional provenance fields (run id/timestamp); report bodies are similarly
stable apart from the manifest timestamps.  Determinism is tested across
thread counts and processes where appropriate.  Random draws come from
ChaCha8, with documented ordering.

Do not confuse a repeated scalar with reproducibility.  Several research
tracks found that a scalar can agree while the underlying registry/order
changes; some estimators now explicitly sort entropy summands as well as state
registries to get bit-identical cross-process results.

### 6.2 Durable output contract

Each ordinary scientific run writes one directory containing:

```text
<out_dir>/<run_id>/
  manifest.json          authoritative lifecycle/provenance record
  metrics.csv            schema-versioned window rows
  report.md              canonical Markdown scientific summary
  snapshots/             optional HGSS snapshots
  causal_events.jsonl    optional causal event log
  leakage.csv, closure.json, guards.csv, ...  optional experiment instruments
```

`manifest.json` moves through explicit run states; UI event delivery is not
authoritative.  `SimEvent` is deliberately bounded and lossy for live display;
`SimStatusEvent` is durable in intent, while the manifest is durable on disk.
An absent GUI receiver must never make a headless run fail.

The CSV has a version comment followed by a stable header.  Missing optional
metrics are empty cells, **not** `0` or `NaN`.  Snapshot v2 (`HGSS`) contains
tagged property values; property-bearing v1 snapshot payloads are not safely
recoverable.  `HGAL` append logs and snapshots treat payloads as opaque bytes
inside `hg-output`.

### 6.3 Eleven-section run report

The Markdown writer emits, in order: manifest, run parameters, campaign
summary, gate status, regime summary, evaluator details, causal language /
constructor ecology, final metrics, locality/leakage, suspicious flags,
observations, and next actions.  Metric labels distinguish `[Measured]` from
`[Estimated]`; preserve this distinction when adding a result.

### 6.4 Training output differs intentionally

A training **rollout** writes nothing and returns in-memory
`RolloutMetrics`.  A **campaign** instead writes one `campaign.csv`, one
`campaign_report.md`, one `campaign_manifest.json`, and serialized champions.
Campaign rows retain failure rows rather than dropping them, include arm
identity, all fitness decomposition, engagement counters, provenance, cost,
and suspicious flags.  A champion is not a scientific result until it is
rerun as a full policy-active validation run.

## 8. How to extend the project safely

### Add or change a rule

1. Put the rule in `rules/` (or an embedded built-in only when it belongs in
   the permanent vocabulary) and give it a minimal configuration.
2. Write a hand-traced fixture for its intended rewrite and a negative/firing
   case for every new guard/effect condition.
3. Characterise bare substrate behavior before using it for ALife, causal, or
   cognition claims: liveness, boundedness, conservation/ledger behavior,
   conflict interaction, initial-condition sensitivity, and run scale.
4. Include deterministic cross-process/thread coverage if it changes ordering
   or consumes RNG.  Be explicit about whether a rule's behavior is an
   attractor, a finite transient, an invariant, or an artifact of the run
   budget.

### Add a metric or causal instrument

1. Decide the causal/mathematical object first: microstate, partition,
   cadence, aggregation, null/control, inclusion rule, and failure meaning.
2. Add the measurement in its layer (`hg-eval` for evaluator metrics,
   `hg-causal` for causal estimators, `hg-observe` for raw observation).
3. Add an output field in `hg-schema::MetricsRow` only when it is a stable
   run-level schema value; propagate it through CSV and report rendering.
4. Provide a positive control, a negative/firing test, reproducibility test,
   and an engagement count.  “The code returned zero” is not a negative
   result unless the instrument was capable of returning nonzero.
5. If it changes a persistent format, update `schema_versions.md` and reader
   behavior deliberately.

### Add a policy, ALife mechanic, or UI feature

- A rule-selection policy implements `hg_observe::RuleSelectionPolicy`; it
  receives snapshots/candidates and returns indices.  Do not let it apply
  writes or resolve conflicts itself.
- Put ALife **dynamics** in a rule file and ALife **bookkeeping/classification**
  in `hg-alife`.  Add any new phenotype/genome interpretation without making
  the crate depend on `hg-engine`.
- A learning campaign must compare budget-matched random, untrained, and
  champion arms.  It needs fitness headroom and a precheck before expensive
  optimization.
- Extend app data through `hg-app-api` DTOs/controllers.  Keep rendering and
  live state on the GUI side, and scientific state in sim-core/observers.

## 10. Substrate / event-alphabet experiments

The A–E tracks use `hg-alphabet` behind an explicit “zero biology” firewall.
They distinguish raw event-symbol count, recurrent symbols, effective alphabet
size, radius refinement, and novelty across time.  The repeated lesson is that
these are different quantities and should not be swapped after observing data.

| Track | State | Findings that remain usable | Qualification / next boundary |
|---|---|---|---|
| A | Complete | Bounded substrates had small effective alphabets (about 1.7–4.1) and time-plateaued novelty; growing rules' large raw alphabets were mostly nonrecurring symbols | Initial architecture-level reading was too strong; radius saturation and time plateau dissociate |
| B | Complete, indicative | Effective alphabet scales linearly with the 1–4 rule series; the per-rule contribution is small | Four points, binding contention, and no fifth composable rule mean this is not a general scaling law |
| C | Complete | `swap` and `cyclic3` create a real third (“partial”) zoo class, so simple flat-vs-growing bimodality is false | Both settle into fixed recurrent sets; `A_eff` is confounded by shares/transient singleton dilution |
| D | Complete | Scaling and priority reversal preserve B's rule-count conclusion; degree-changing `rewire_bounded` remains rich but frozen | Universal arity-1 `influx` means the intended no-contention substrate is structurally unreachable |
| E | Complete / hard stop | The new variable-to-variable degree primitive enabled `rebalance`; it too has a byte-identical recurrent alphabet over 16× horizons | `rebalance` rapidly contracts toward a conserved degree sequence; this closes the planned F-track, not all possible rule designs |

**Current synthesis.** The measured zoo supports “a fixed tested rule file
reaches an attractor with a finite recurrent event context set,” even for
conservation, bounded degree change, substrate labels, and self-balancing
change.  It does *not* establish that the architecture can never sustain
open-ended novelty: B found per-rule linear scaling and the available series
is small.  Future work should lead with recurrent count and report `A_eff` as
a companion rather than the headline.

## 11. ALife experiments: ecology, selection, and CE

### 11.1 Experiment 5 and follow-ups

| Experiment | State | Result |
|---|---|---|
| 5 / S6 | Complete; S7 gate cleared with caveats | All seven original ecology criteria were met: static-substrate, spontaneously replicating, turning-over carriers with reproducibility/accounting.  The original selection criterion was later downgraded to a **degenerate-only** node-funded threshold collapse; the stable band is seed-fragile. |
| 5b active traits | Complete negative | Genome-scaled maintenance collapses toward zero, makes carriers effectively immortal, and destroys turnover.  Activating more traits without an opposing cost does not rescue selection. |
| 5c parent-funded replication | Complete partial success | Parent payment creates a real interior replication-threshold optimum and preserves turnover, but energy-rich lineages can still fall into a floor basin. |
| 5d proportional reproductive tax | Complete bounded success | Pulls even rich, behaviorally relevant lineages toward the optimum; an already deep, always-satisfied threshold is causally inert and therefore immune to an energy cost. |
| 5e reproductive senescence | Complete limit characterisation | Improves marginal cases but cannot remove the deep inert sink.  In unclamped trait space the minority sink is provably irreducible by the tested cost/mortality levers. |

The stable final statement is precise: **non-degenerate selection exists for
lineages whose threshold still controls reproduction; a deep unclamped,
always-satisfied threshold is an irreducible drift sink.**  Do not restate the
earlier scorecard as evidence of universal open-ended selection.

### 11.2 Experiment 6: causal emergence across replication

| Experiment | State | Result |
|---|---|---|
